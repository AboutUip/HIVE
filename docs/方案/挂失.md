## 结论

挂失有两条路，后续恢复相同。中央强制挂失，或节点自己申请挂失。挂失之后，指向它的地址挂起，针对它的请求停住，不读取它自己的库。

## 过程

下面任一情况都算这台服务节点不可用：

1. 未按预期上报，中央索取和重试之后仍无法访问。
2. 节点自己报告运行错误。
3. 节点自己发现数据库不可达。
4. 服务器不可达。

两条路：

1. 中央强制挂失：上报超过期限，索取失败并完成重试。连续两次联系不上，就挂失。
2. 节点申请挂失：运行错误或数据库不可达，由那台节点自己提出。库坏了只由那台节点自己发现并申请。

挂失之后：

1. 中央通知各节点这台已经挂失。
2. 指向它的地址挂起。
3. 其他节点把指向它的请求停住，不发出。
4. 还留在它待上报队列里、中央从未收下的日志，不在挂失时补交。
5. 同一时间只进行一次装入。装入规则见 [恢复](恢复.md)。

其他节点的读取逻辑不变：那里没有，就认定没有。已经挂起的地址则是停住，不是改口说没有。

## 例子

华北超过期限。中央向它要日志，失败一次，再失败一次。华北被标成挂失。华东手里指向华北的地址变成挂起。华东再读林夏的城市时，请求不发往华北。

若华北在写入时发现自己的库抛错，它向中央申请挂失。后续和上面相同。

## 边界

- 对齐中的节点不走挂失。
- 已经挂失的编号保持挂失。它再来登记，不会被清成正在服务。
- 已经有一台节点在装入时，不能再挂失另一台，除非这次挂失的正是那台接替节点。见 [恢复](恢复.md)。
- 灾备节点不走这条挂失。

调用见 [中央](../接口/中央.md)。核对时的强制挂失和故障标记见 [恢复](../核对/恢复.md)、[故障](../核对/故障.md)。
