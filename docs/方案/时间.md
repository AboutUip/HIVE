## 结论

时间是这台节点在写入或删除那一刻发下的混合逻辑时钟（HLC）：物理位是它自己的 UTC 毫秒，逻辑位区分同一毫秒里的先后。节点收到别的节点的时间戳时，会先把自己的推进到更晚，再给下一次写入发号。同一键有多份时，时间更晚的留下。

## 过程

1. 每台服务节点维护一个 HLC。写入或删除时发下一个严格递增的时间戳，格式是物理位加六位逻辑位，例如 `2026-04-01T00:00:00.000Z-000007`。
2. 这个时间随日志交给中央，也写在地址上。
3. 中央比较已有地址和这条日志的时间，时间更晚的留下。比较就是字符串比较，格式已经排好序。
4. 节点收到任何一条带时间戳的消息（索引、装入的数据），先把自己的时钟推进到至少比它晚，再继续服务。这样，因果在后的写入必然拿到更晚的时间，和墙钟准不准无关。
5. 时间相同的，后被中央收下的那一份留下。相同的时间只可能来自两台从未互发过消息、物理时刻又恰好一致的节点。

写入不记录它基于哪一版。要审计时，在中央选择把用过的日志写成文件，不在数据上再加版本号。

## 例子

华北在 `2026-04-01T00:00:00.000Z-000000` 写下城市「北京」。华东收到这份地址后，即使自己的墙钟落后华北一小时，它下一次写下城市「上海」的时间戳也必然晚于华北的那份。中央收下两份之后，地址指向华东，值以「上海」为准。

若华北在同一毫秒里连写两次，第二次的逻辑位加一。后一次留下。

## 边界

- 并发（互不知晓）的两份写，谁留下由 HLC 决定，不再由墙钟决定。顺序与消息交换的因果序一致，不保证与「人先按下哪次回车」一致。
- 节点重启后，从库里已有的最大时间戳恢复，重启后的发号仍然单调。
- 升级前写下的纯 UTC 时间戳（没有逻辑位）照常参与比较，排在同毫秒的 HLC 之前。
