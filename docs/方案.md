# 方案

本文描述产品行为。调用方式、参数和返回值见 [API.md](API.md)。文档目录见 [README.md](README.md)。

## 组成

系统里有三类角色。

中央是唯一核心。它接收各节点的日志，维护全局地址，把地址派发给服务节点，把日志收成稳定数据交给灾备，接纳新节点，并处理挂失。中央不长期保存日志内容。日志用完就删除。只有明确要求留档时，才另写成日志文件。

服务节点保存用户在本机产生的数据，保存自己已经收到的地址副本，并按周期向中央上报。一台服务节点同时是自己的数据所在地，也是一份索引。读取只信本机，不在读取时回头问中央。

灾备保存整理后的稳定数据，用来在节点挂失后恢复。它不是日志仓库，也不参与普通读取。

用户进入哪个区域，就落到这个区域的服务节点。就近沿用 CDN 那种「指向附近」的结果。本方案不另做测距。VPN 一类跨区域伪装不在服务范围内。

一次读写最多经过一层：落到的节点上有数据，就在本地完成；没有，就按本机索引直接向持有数据的那一台去取。灾备和挂失恢复要经过中央，这是另一条路，不拿来做普通读写。

## 数据写在产生它的地方

用户在某台服务节点上写下的内容，只保存在这台节点的库里。同一份内容同时成为一条完整日志，留在这台节点的待上报队列中。这次访问不等待上报结束。

待上报一直留到中央确认。中央负责过滤。同一条已经收过的日志再次到来，中央滤掉，并确认节点可以把它从队列里删掉。节点不在送出之前自己删掉队列。

例子。人在华北写下 A、B、C。这三份都在华北。人后来到华东，把 C 改掉并新写 D。华东只保存新的 C 和 D。同步完成前，华北仍是原来的 A、B、C。同步之后，华北按时间去掉被盖住的旧 C，地址把 C 和 D 指到华东。没被改过的 A、B 仍在华北。

## 读取

读取按下面的顺序进行。

1. 本机库里有这份数据，直接使用。
2. 本机没有，查本机的地址副本。有地址，就到那个 IP 把数据取回来用，不写入本机。
3. 本机没有，地址副本里也没有，视为没有，拒绝。
4. 地址指向的节点上已经没有这份数据，视为没有，拒绝。不改去灾备里找。

「从未写过」和「还在同步窗口里、别的节点尚未知道」使用同一种拒绝。窗口应当短于一个人在区域之间的移动。为这短短一段去区分两种拒绝，代价高于等这次同步。代码可以造出这种拒绝，服务里就当没有。

地址已经挂起，或者目标节点已经挂失，则请求停在原地，不发往那台节点。这和「没有」是两件事：前者是已知地址被冻结，后者是认定没有这份数据。

同步窗口内，别的节点可能还拿着旧地址，于是取到旧值。这是方案接受的窗口。窗口长度可以调整，调整必须通知中央。

## 时间

时间是数据在那台节点上产生的那一刻，使用 UTC。各节点自己记这个时间，不和中央对时，也不使用中央发放的序号。

同一键有多份时，时间更晚的留下。时间相同的，后被中央收下的那一份留下。同一台节点不会给自己的连续两次写入打出同一个时间：若两次落在同一毫秒，后一次记成更晚的时刻。

写入不记录它基于哪一版。要审计时，在中央选择把用过的日志写成文件，不在数据上再加版本号。

## 索引

索引只回答：这个用户的这个键，现在在哪一台、哪个别名、哪个 IP、什么时间、是否挂起。索引不存放值。

中央根据收下的日志更新全局地址，再派发给其他服务节点。交上这份日志的那一台不接收这次派发。因此，一台节点的持久索引里，通常没有它自己刚写下、还没被别的节点改过的那些键。那些键以本机库为准。

派发时，时间不早于本机现有地址的，才覆盖本机地址。新地址指向别处，且时间不早于本机那份数据时，本机删掉这份过时数据。

某次派发若有节点没收到，读取时不向中央追问。地址仍留在中央。这台节点下次按周期来上报时，中央把尚未确认送达的地址再送一次。中央删除的是日志内容，不是地址。

## 完整名单

点名读取一个已知的键，会先看本机库，所以自己写下的数据读得到。

列出「这个用户有哪些键」时，只翻持久索引会漏掉本机写下、又从未被派发回来的键。列完整名单时，在已有索引上临时补上本机库里的数据，地址指向自己。同一键两边都有时，以本机库里的这份为准。这张临时表用完即弃，不写回持久索引。

新节点来拉索引时，用的也是这张临时表。

## 上报

每台服务节点有自己的上报周期。中央知道每一台的周期，并赋予一段容错。

到了周期就要上报。没有新日志，也要报一次空的。空上报表示这台节点还在，中央据此重新计算下一次期限。

超过「周期加容错」，并且没有收到这台节点修改窗口的通知，中央主动向它要日志。要不到就重试。仍然无法访问，中央强制挂失，并进入灾备恢复。

节点修改自己的上报周期，或统一调整上报与灾备窗口时，必须通知中央。通知之后、新周期生效前的那段空档，不算漏报。

## 灾备

灾备和索引分开。索引的量级是地址。灾备留下可以用来恢复的稳定数据。

每台灾备事先声明自己负责哪些服务节点。负责范围在整理日志时生效。某个键再次被整理时，若它的所在节点不在这台灾备的负责范围内，这份记录离开。只修改负责范围、又没有这个键的新日志，不会立刻重扫已经收好的记录，也不会把以前没有收进来的数据补回去。

新加入的服务节点不会自动进入任何灾备的负责范围。必须明确声明，并且至少再经过一次灾备整理。声明之前产生、又没有在声明之后再次被整理到的数据，不会补进这台灾备。

中央在更长的窗口里，把尚未用完的日志按用户和键收成最新的一份，交给负责其当前所在节点的灾备。不把原始日志打包送去，也不做压缩包。整理完成，这些日志从中央删除。要求留档时，删除前把它们写入日志文件。

## 新节点

新节点先连上中央，状态为对齐中。中央给它一块缓冲区。它从当前负载最低的、正在服务的节点拉索引。负载按本机数据份数计算，份数相同则取编号较小的一台。

拉来的是一张临时表：来源节点已有的地址，加上来源节点自己库里的数据地址。同一键以库里的那份为准。临时表不写回来源节点。

对齐期间，新的地址先进入缓冲区，不直接写进这台新节点。它还不能读写服务。就绪之后，缓冲区补进它的索引，然后开始服务。

就绪并不使它自动获得灾备。负责范围要另外声明，并再等一次灾备整理。

## 挂失

下面任一情况都算这台服务节点不可用：

- 未按预期上报，中央索取和重试之后仍无法访问
- 节点自己报告运行错误
- 节点自己发现数据库不可达
- 服务器不可达

挂失有两条路，后续恢复相同。

- 中央强制挂失：上报超过期限，索取失败并完成重试。
- 节点申请挂失：运行错误或数据库不可达，由那台节点自己提出。

库坏了只由那台节点自己发现并申请。其他节点的读取逻辑不变：那里没有，就认定没有。

挂失之后：

- 中央通知各节点这台已经挂失。
- 指向它的地址挂起。
- 其他节点把指向它的请求停住，不发出。
- 还留在它待上报队列里、中央从未收下的日志，不在挂失时补交。
- 恢复不读取这台节点自己的库。

同一时间只进行一次装入。

## 恢复

恢复是数据恢复和所有权转移，不是临时接替。

中央选择一台正在服务、负载较低的节点来接收数据，不按地理远近。这台节点在装入期间继续提供自己原来的服务。

装入前，中央先取出灾备里属于挂失节点的稳定数据。若中央这时还留着相关日志，先把这些日志再整理进灾备一次，把中央已经收下、尚未整理的内容纳入，以减少丢失。然后再按更新后的灾备装入。这次使用结束，日志按原规则删除。

装入按时间合并。接替节点上已有的数据更晚，就留下本机这份；否则写入灾备里的值。灾备里没有的键继续挂起，不造出一份数据。

因为相关请求已经停住，装入不使用新节点那种缓冲区。装入完成前，不接受针对这台挂失节点的请求。完成后，各节点的地址改为接替节点，并解开这些挂起。若某台灾备没有声明负责接替节点，挂失节点留在那台灾备上的对应记录移出。

接替节点在装入完成前也不可用：立刻回退尚未完成的装入，再把这台接替节点标记挂失。已经取到并更新过的灾备数据留下。原来的挂失仍然有效。之后可以再选一台还在服务的节点，继续把同一份灾备数据装入。

## 挂失节点回来

挂失节点恢复在线后，清空自己的数据，作为一台新节点重新加入：重新对齐索引，使用新的身份。旧身份保持挂失。灾备已经把所有权交给接替节点，不把旧库重新当成数据来源。

回来时若装入还没结束，先完成或回退这次装入，再把这台机器当成新节点。

## 别名和 IP

每台节点在中央有稳定别名，也有当前 IP。地址里两样都记。

普通访问直接使用 IP，这样路径仍是一层。IP 变化很少。IP 无法访问时，才拿别名向中央要一次当前 IP，更新本机持有的地址，然后再连。不在每一次访问时都用别名绕到中央。

中央自己的节点记录和全局地址会改成新 IP。已经派发出去的地址副本仍用旧 IP，直到某次访问发现不通，再按别名更新。

## 删除

持有这份数据的节点可以删除这个键。删除与写入一样产生日志，时间规则相同。本机数据立即去掉。其他节点要等这次上报和派发之后，才从地址里去掉它；灾备要等下一次整理，才去掉对应的稳定数据。

何时删除由业务决定。本方案只提供删除这个键的能力，不规定业务策略。

不能在一台并不持有该数据的节点上删除它。

## 中央本身

中央的位置不因挂失和灾备而改变。节点挂失时，恢复的是服务节点上的用户数据，不是把中央换掉。

若要中央自己也能承受故障，在本方案之外为它增加灾备，或采用传统的全量复制。那是部署选择，不改变上面的读写、索引和节点恢复规则。
